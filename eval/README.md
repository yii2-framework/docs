# Agent evaluation

This directory tests the documentation, not a model. The historical runner injects `llms.txt` and a skill body; the native-client workflow below installs the skill
instead. Both use canonical task contracts and deterministic checks of the files produced.
It is the documentation equivalent of a mutation test: when a page or a skill is wrong, incomplete, or misleading,
a task fails. It implements criterion 7 of the plan, run locally with Claude Code headless instead of in CI.

## Native skills: Claude, Codex and OpenCode

Tasks `09-dialog-options`, `10-toast-migration` (criterion A2), and `11-filepond-avatar` (criterion A1) use local
Markdown generated by the site. Build after synchronizing package guides and canonical package skills. The core
skill remains in `skills/yii2-framework`; extension skills are generated into `.cache/skills/` from their packages.
There is no manually maintained extension skill copy in this repository.

Version 1 remains the default: its task definitions and historical results are unchanged. New evaluations can opt
into `--task-version v2` for tasks 09-11 under `tasks/v2/`, criterion B1. Every v2 task body explicitly requires
`declare(strict_types=1);`. Task 10 uses a PHP token check that accepts grouped class imports and aliases instead
of a textual namespace grep. The documentation set and functional widget/upload requirements stay the same.

Preparation records `task_version` and `task_definition_sha256`. Use the same version in `check.sh`; copy the
prepared metadata alongside the outputs so the checker can reject another version or a changed contract. Metadata
without a version denotes v1. Reference fixtures are separate under `fixtures/v2/pass/`. Do not re-score historical
runs with v2 or compare them as if their task-body hashes were identical. The historical injected runner keeps its
existing v1 task selection.

Formatting-only Markdown maintenance can change task-definition and prompt hashes without changing acceptance
requirements. Prepare a new run against the formatted definition; do not rewrite historical metadata to bypass
the contract-hash check.

Preparation makes no client, provider or model call:

```bash
npm run sync:local
npm run build
workspace=$(mktemp -d /tmp/yii2-native-codex.XXXXXX)
node eval/prepare-native.mjs --client codex --activation auto --task 09-dialog-options --task-version v2 \
  --workspace "$workspace" --model gpt-6-luna --effort medium
```

Repeat with a **new empty workspace** for each task, client and condition. Use `--client claude --model sonnet`, or
`--client opencode --model <approved-provider/model#variant>`. OpenCode has no assumed provider or model. Do not
interpret the placeholder as approval to connect an account, accept provider terms or incur API charges.
`--docs-source <dist>` and `--skill-source <skills-root>` accept explicitly selected local sources. The skill root
contains `<task-skill>/SKILL.md`; by default preparation resolves the core source or generated extension source.
Symlinks in prepared source files are rejected; workspaces must be empty real directories.

The preparation copies only task-declared pages, writes `.eval-docs/INDEX.md` with bytes and SHA-256 hashes, installs
the exact skill tree at `.claude/skills/<name>`, `.agents/skills/<name>`, or `.opencode/skills/<name>`, and seeds the
legacy view for task 10. `.eval-run/` records the unchanged task-body hash, prompt hash, protected input hashes,
output contract, reviewable argv/command template and stage metadata. Preparation is not discovery or activation.

In `auto`, the prompt is exactly the task body. In `explicit`, it adds only the native invocation: `/name` for
Claude, `$name` for Codex, or a request to use OpenCode's native skill tool. No skill body or API catalog is injected.
Compare automatic runs across clients with the same body hash. Explicit runs necessarily differ in invocation.

| Stage                  | Required evidence                                                                                                                                                                                                                                                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Installation           | Prepared skill path and matching source hashes.                                                                                                                                                                                                                                                                                                                    |
| Discovery              | Client's available-skill catalog includes the intended name and prepared origin.                                                                                                                                                                                                                                                                                   |
| Activation             | Client-specific evidence links discovery to actual loading for this task. For Claude/OpenCode retain native skill-tool events; for Codex retain the discovered origin and a trace containing the complete matching prepared skill body. An explicit prefix requests use; it does not prove loading. A generic filesystem read or self-claim alone is insufficient. |
| Selective consultation | Trace records `INDEX.md` first and the local pages actually read; preserve page hashes.                                                                                                                                                                                                                                                                            |
| Functional acceptance  | Copy only declared outputs into the checker run tree; run `check.sh` and record pass/fail/skip independently.                                                                                                                                                                                                                                                      |

Before real runs, confirm client versions/options, the exact model identifier and authentication mode without
printing tokens. `codex login status` must report ChatGPT, and generated Codex arguments force that login method;
an accessible subscription does not authorize a separate API provider or bill. Check current quota separately.
OpenCode's selected provider, free-period limits, privacy terms and whether weights are open must be reviewed before
sending a prompt. Free price and open weights are separate properties.

The command templates do **not** prove isolation. Native discovery must remain enabled, so disabling all skills or
injecting the body is not an equivalent test. Exclude unrelated home instructions, global skills, plugins, hooks,
MCP servers, private configuration and environment secrets before execution; verify model-visible prompt origins
with an offline preflight. `--ignore-user-config` preserves Codex authentication but does not by itself establish
that home `AGENTS.md` and user skills are absent. Do not execute when that exclusion cannot be established. Use a
bounded timeout and write event logs outside the model's workspace. Do not alter global settings or credentials.
When Codex shell environment inheritance is `none`, supply an explicitly approved public `PATH` through
`shell_environment_policy.set` if shell utilities are needed. Keep the other environment variables excluded;
successful discovery does not prove tools have a usable search path. Command templates still need isolation review
for the selected host and client version.

After a reviewed, isolated client run, copy only expected files, for example:

```bash
run=$(mktemp -d /tmp/yii2-native-results.XXXXXX)
mkdir -p "$run/09-dialog-options/files/resources/views/site"
cp "$workspace/resources/views/site/_terms.php" "$run/09-dialog-options/files/resources/views/site/"
cp "$workspace/.eval-run/meta.json" "$run/09-dialog-options/meta.json"
eval/check.sh "$run" --task 09-dialog-options --task-version v2 --out "$run/checks"
```

Before copying, compare protected inputs with their hashes and report every workspace path changed outside the
output contract. A pass in `check.sh` says nothing about activation. A missing app or extension produces skipped
checks; do not count a task with skipped semantic checks as a full functional pass. Record client, provider, resolved
model, effort/variant, task criterion, hashes, wall time, quota/list-price information and each stage separately.
Historical curated reports under `internal/` remain observations of their original client/model and task versions;
do not reclassify old runs or read private session logs to populate a new run.

The FilePond fixture and semantic probe require `ext-fileinfo` and the installed FilePond extension. `setup.sh`
accepts `FILEPOND_PATH` and installs it in the throwaway checker application. For a writable existing app copy,
`check.sh` accepts `EVAL_APP_DIR`, `EVAL_PRISTINE_DIR` and `EVAL_STATE_FILE`; no model sees those application dependencies.

```bash
eval/check.sh eval/fixtures/v2/pass --task 11-filepond-avatar --task-version v2 --out /tmp/filepond-acceptance
node --test --test-isolation=none --test-reporter=tap scripts/eval-native.test.mjs
```

The probe checks effective JavaScript options, real MIME detection, extension and decoded-size validation,
malformed/multiple/empty values, the exact decimal 2,000,000-byte size boundary, absence of writes on invalid input,
and exact PNG bytes saved as `avatar.png` despite
a forged client type and mismatched allowed extension. It does not run an interactive browser or prove the editor's
visual crop quality. Deterministic regression tests mutate MIME validation, client-transform and validation ordering
independently to demonstrate that the acceptance boundary rejects each defect. Equivalent numeric size and square
ratio representations pass the same contract; a looser 2 MiB server limit fails it.

## Historical injected-skill runner

The rest of this file documents the existing Claude-only injected/baseline experiment. It does not run native skill
activation and must not be mixed with the native conditions above.

## Prerequisites

- PHP 8.3 or later with `pdo_sqlite`, Composer 2, `rsync`, `curl`, and GNU `timeout`.
- Claude Code (`claude`) logged in with the maintainer's subscription. No API key is used.
- `dist/llms.txt` from `npm run build`, or the preview server (`npm run preview`, `http://localhost:4321/docs/`).
  While the public site does not serve `index.md` pages, the runner rewrites the documentation URLs in the prompt to
  the preview server, so keep it running during a model run.
- For tasks 06-08: `yii2-extensions/bootstrap6`. It is not on Packagist yet, so `setup.sh` installs it from a local
  clone (`BOOTSTRAP6_PATH`, default `../yii2-extensions/bootstrap6` next to the `yii2-framework` directory).

## Run

```bash
eval/setup.sh                                    # once: creates eval/app and eval/.cache/app-pristine
eval/run.sh --dry-run                            # assembles every prompt; calls no model
eval/run.sh --task 08-alert-theme --model sonnet # one task, then check.sh on the run
eval/run.sh --model sonnet                       # all tasks
eval/check.sh eval/out/<timestamp>               # re-run the checks of an existing run, no model call
eval/check.sh eval/fixtures/pass --out eval/out/fixtures-pass   # verify the checker itself
eval/check.sh eval/fixtures/pass --task 04-active-form-view --out eval/out/application-flow
```

`run.sh` options: `--task <id>` (repeatable), `--model <alias>` (default `sonnet`), `--effort <level>`,
`--budget-usd <n>` (per task, default `1.00`), `--timeout <seconds>` (default `900`), `--docs-base
auto|public|local|<url>`, `--dry-run`, `--no-check`, `--no-skill`. Run `eval/run.sh --help` for details.

`--no-skill` runs the baseline condition: the prompt omits the `<skill>` block and the words "and the skill" in the
documentation sentence, and nothing else changes (same command line, `llms.txt`, and fresh workspace). `meta.json`
records the `condition` (`skill-injected` or `no-skill`). The runner refuses to start a task if its workspace is not
empty.

Each task runs `claude -p` in a fresh temporary directory with the user's CLAUDE.md, skills, plugins, hooks, MCP
servers, and settings disabled (`--safe-mode --restricted --strict-mcp-config`), only the file tools and `WebFetch`
for the documentation host, no shell, and a dollar cap. `command.txt` in each task directory records the exact
command line.

## Results

```text
eval/out/<UTC timestamp>/
  llms.txt                     the index the run used (rebased URLs)
  summary.md, summary.json     pass/fail per check, totals, task pass rate, reported cost
  results.tsv                  one row per check: task, check, status, detail
  <task-id>/prompt.md          the exact prompt sent on stdin
  <task-id>/command.txt        the CLI command line
  <task-id>/result.json        the CLI JSON result (answer, turns, usage, cost)
  <task-id>/meta.json          wall time, exit code, docs base, and the usage fields of result.json
  <task-id>/files/             what the agent wrote
  <task-id>/checks/            check logs, phpstan.neon, rendered HTML
```

`eval/out/`, `eval/app/`, and `eval/.cache/` are ignored by Git.

When a task changes its acceptance contract, its optional `criterion` frontmatter value identifies the new version
in future `meta.json` files without rewriting historical runs. Task 10 uses criterion A2: both `yii\helpers\Html`
and `yii2\extensions\bootstrap6\Html` satisfy its encoding requirement because the extension helper inherits the
same `encode()` implementation. The `pass-yii-html` and `fail-no-encoding` fixture roots exercise that boundary.

The last command reproduces the deterministic form, validation, migration, SQLite persistence/reload, rendering,
and XSS-encoding flow without calling a model. See [AI application flow](ai-application-flow.md) for its recorded
result, limitations, and the remaining native-client evaluation work.

Tasks may declare a small generated documentation set in their `docs` frontmatter list. Prepare those Markdown pages
for an isolated workspace without a model or network request:

```bash
eval/prepare-local-docs.sh 09-dialog-options /path/to/workspace
```

The command copies only the declared files from `dist/` to `.eval-docs/` and writes `INDEX.md` with each page's byte
size and SHA-256 hash. It refuses to overwrite an existing `.eval-docs/` directory. This is a local `Read` workflow,
not evidence that `WebFetch` can access the preview server.

## Cadence

The evaluation runs on the maintainer's machine with the Claude Code subscription; there is no CI job, because a
CI run would need an API key.

1. Run all tasks once a week, and also after a change to `skills/`, to the `llms.txt` generation, or to a guide page
   that a task lists in `context`:

   ```bash
   eval/run.sh --model sonnet
   ```

   While the public site does not serve `index.md` pages, build the site and keep `npm run preview` running first
   (see Prerequisites).

2. Record the run in `internal/research/eval-runs/<YYYY-MM-DD>.md` (git-ignored, template in the README of that
   directory): the totals and the task table of `summary.md`, the cost, and a triage line for every failed task.
3. Phase 1, report only: until three full runs are recorded, the results are a report and block nothing.
4. Phase 2, gate: from the fourth run on, a run passes when at least 7 of the 8 tasks pass on Sonnet and no task
   fails in two consecutive runs.
5. Triage every failed task as one of:
   - documentation gap: fix the guide page, the PHPDoc behind the API reference, or the skill;
   - task or check defect: fix `eval/` and record why (a wrong reference solution, a check that is too strict);
   - model error: record it only.

   Never weaken a task to make it pass. When a task flips between pass and fail, re-run only that task twice
   (`--task <id>`) before acting.

## Checks

| Check                         | Passes when                                                                                                                                                                |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `outputs`                     | every path in `outputs` exists and is not empty                                                                                                                            |
| `php-lint`                    | every `*.php` passes `php -l`                                                                                                                                              |
| `strict-types`                | every `*.php` declares `strict_types=1`                                                                                                                                    |
| `grep:<ERE>`                  | the extended regular expression matches at least one output file                                                                                                           |
| `php-import:<FQCN>`           | PHP tokens declare the class import, including grouping/aliases, or fully qualified class access; comments, strings, function/constant imports and trait uses do not count |
| `no-forbidden:<ERE>`          | the expression matches no output file                                                                                                                                      |
| `app-boot`                    | with the seeds and outputs copied into `eval/app`, `./yii help` exits 0 (see the note below)                                                                               |
| `app-migrate`                 | `migrate`, `migrate/down 1`, and `migrate` succeed (SQLite)                                                                                                                |
| `app-probe:<probe>:<arg>`     | `lib/probe.php` passes a named semantic probe, including ActiveRecord validation and persistence                                                                           |
| `app-render:<view>`           | the view renders without an exception; `$model` is a `Post` whose title is an XSS payload                                                                                  |
| `app-static`                  | PHPStan level 5 (`EVAL_PHPSTAN_LEVEL`) reports nothing on output PHP under `src/`, `config/`, and `resources/views/`                                                       |
| `html:<ERE>`, `no-html:<ERE>` | the rendered HTML matches, or does not match, the expression                                                                                                               |
| `js:<ERE>`, `no-js:<ERE>`     | the head and body HTML of the registered scripts matches, or does not match, the expression                                                                                |

`app-boot` also reports `composer static` as `app-boot:composer-static`; it is skipped while the pristine app fails
it (the template archive omits `phpstan.neon`), and `app-static` replaces it.

`eval/app` is restored from `eval/.cache/app-pristine` before and after each task, so tasks never see each other.
A task passes when none of its checks fails; skipped checks (for example, no app) do not count.

## Add a task

1. Create `eval/tasks/NN-<slug>.md` with frontmatter and the prompt as the body:

   ```yaml
   ---
   id: NN-slug # equals the file name
   title: Short title
   criterion: A1 # optional acceptance-contract version recorded in meta.json
   skill: yii2-framework # a directory under skills/
   context: # optional: index.md URLs to list in the prompt
     - https://yii2-framework.github.io/docs/guide/<page>/index.md
   docs: # optional: generated Markdown paths copied into an isolated workspace by prepare-local-docs.sh
     - extensions/bootstrap6/reference/dialog/index.md
   outputs: # files the agent must write, relative to the app root
     - src/controllers/FooController.php
   workspace: # optional: directories under eval/workspace/ copied into an isolated workspace by prepare-local-docs.sh
   seed: # optional: directories under eval/seed/ copied into the app first
     - post
   checks:
     - outputs
     - php-lint
     - 'grep:SomeClass::method\('
   ---
   ```

   Quote values that contain `:`, `'`, `\`, or `#` with single quotes (`''` is a literal quote). Double quotes are
   not supported.

2. Write the prompt as a user would: state the goal, the constraints, and the files to write. Never name the class,
   method, or option that the checks look for.
3. Add a reference solution in `eval/fixtures/pass/<id>/files/` and, ideally, a wrong one in
   `eval/fixtures/fail/<id>/files/`; run `eval/check.sh` on both and confirm pass and fail.

## Cost

The smoke run of `08-alert-theme` on Sonnet took 2 turns, 7 seconds, about 47k input tokens (mostly cached), and
reported 0.10 USD at list price (`total_cost_usd`). A subscription pays for it within its usage limits; the figure is
an estimate, not a charge. Expect roughly 1 to 3 USD of list price for all eight tasks, more when the agent fetches
pages. `--budget-usd` caps each task. The CLI has no documented turn limit, so `--timeout` bounds the wall time.

## PSR bridge worker case

Task `12-psr-worker-lifecycle` (v1 contract, explicit strict types, B1 criterion) exercises a custom worker with
lazy sessions and post-emission finalization. It uses an already installed package checkout rather than the
Bootstrap/FilePond application fixture; the checker never installs dependencies or contacts a provider.

```bash
EVAL_PSR_BRIDGE_PACKAGE=/absolute/path/to/psr-bridge bash eval/check.sh eval/fixtures/pass \
  --task 12-psr-worker-lifecycle --out /tmp/psr-worker-reference-check
EVAL_PSR_BRIDGE_PACKAGE=/absolute/path/to/psr-bridge node --test scripts/eval-psr-bridge.test.mjs
```

The runtime probe alternates visitors, verifies signed and malformed cookies, strict mode, missing-cookie
isolation, and success/failure/after-send-exception paths. Negative fixtures prove it rejects missing, repeated,
and premature finalization and insecure configuration. With no package path, runtime tests are reported as
skipped; native preparation tests still run offline.

Prepare separate `explicit` and `auto` workspaces with `eval/prepare-native.mjs --task 12-psr-worker-lifecycle`,
using the same task body, skill bytes, and generated local docs for each condition. The existing client preparation
supports Claude Code, Codex, and OpenCode. Preparation does not prove native discovery or invoke a model.
Use only an authorized subscription and previously verified client isolation; do not copy credential databases,
create new authentication, or infer activation merely because the generated code passes. Retain raw output,
protected-input hashes, discovery/activation evidence, and failures without editing the model's answer.
